# Obsidian Hub 项目规划

> 状态：MVP 规划已确认，尚未进入实现  
> 平台：Windows 11 优先  
> 更新日期：2026-07-15

> 当前实施策略：将 M1 数据闭环与第一批 M2 启动体验合并为“启动器核心版”，避免先制作过渡表单再重复改造 UI。

## 1. 一句话定义

Obsidian Hub 是一个在 Obsidian 加载任何仓库之前运行的轻量桌面启动器，让多仓库用户先选择目标仓库，再直接进入对应工作空间。

## 2. 问题与机会

### 2.1 用户问题

Obsidian 默认延续最近使用的仓库。多仓库用户想进入另一个仓库时，往往需要：

1. 先启动上一次使用的仓库。
2. 等待该仓库的主题、索引与社区插件初始化。
3. 再打开仓库切换器。
4. 选择真正需要的仓库。

当上一次使用的是插件很多的主仓库时，这段无效等待尤其明显。

### 2.2 根因

普通 Obsidian 插件只能在某个仓库已经被选定并开始加载后运行，因此无法真正拦截“启动前选择仓库”。独立启动器可以把选择动作提前到 Obsidian 进程启动之前。

### 2.3 核心假设

如果启动器能够快速、可靠地展示仓库并支持键盘直达，用户会愿意把它固定到任务栏，替代 Obsidian 原始图标成为日常入口。

### 2.4 成功信号

- 用户能够在启动器出现后 3 秒内选中并打开目标仓库。
- 从启动器操作到系统接收 Obsidian URI 的中位耗时低于 300 ms，不含 Obsidian 自身加载时间。
- 日常使用中无需先加载错误仓库。
- 核心流程完全支持键盘，不强迫用户使用鼠标。
- 连续使用一周后，用户愿意保留任务栏入口。

## 3. 已确认的产品决策

| 决策     | MVP 选择                | 原因                               |
| -------- | ----------------------- | ---------------------------------- |
| 平台     | Windows 11 优先         | 对准当前真实环境，缩短验证周期     |
| 仓库录入 | 仅手动添加              | 避免扫描复杂度，先验证核心启动价值 |
| 视觉     | Obsidian 原生感         | 降低学习成本，形成连续的使用体验   |
| 产品形态 | 独立 Tauri 应用         | 在 Obsidian 仓库加载前运行         |
| 配置存储 | AppData 中的版本化 JSON | 数据规模小、透明、易备份与迁移     |
| 仓库访问 | 默认只读                | 启动器不应侵入用户知识库           |

“Obsidian 原生感”只指视觉语义和交互习惯，不代表依赖 Obsidian 内部样式，也不等于官方兼容认证。

## 4. 用户与场景

### 4.1 核心用户

- 长期、熟练使用 Obsidian。
- 同一设备管理多个用途不同的仓库。
- 主仓库启用大量插件，冷启动较慢。
- 经常在主仓库、项目仓库、临时仓库之间切换。

### 4.2 核心场景

#### 场景 A：打开轻量仓库

用户上次使用主仓库，现在只想快速进入临时仓库。启动 Hub、搜索仓库、回车，主仓库完全不参与此次启动。

#### 场景 B：在相似仓库中定位

用户有多个项目仓库。启动 Hub 后直接输入项目名，列表实时过滤，选择目标并打开。

#### 场景 C：常用仓库直达

用户收藏 3 个高频仓库。Hub 默认先展示收藏项，方向键选择并回车打开。

#### 场景 D：仓库路径已经移动

Hub 检测到原路径无效，不发送错误启动请求，而是提示编辑路径或移除条目。

## 5. MVP 范围

### 5.1 必须具备

1. 首次启动空状态与添加仓库入口。
2. 使用系统目录选择器选择仓库文件夹。
3. 校验目录存在且包含 `.obsidian` 子目录。
4. 添加仓库名称和可选描述。
5. 仓库列表、搜索和空搜索结果。
6. 收藏与取消收藏。
7. 最近打开时间记录与排序。
8. 编辑仓库信息和移除条目；移除只影响 Hub 配置，不删除磁盘文件。
9. 通过 Obsidian URI 打开仓库。
10. 重复路径、无效路径、名称冲突和协议不可用反馈。
11. 深色、浅色和跟随系统主题。
12. 键盘导航、焦点态和基础无障碍语义。

### 5.2 明确暂缓

- 自动扫描与 Obsidian 内部注册表导入。
- 托盘、开机启动、全局快捷键、单实例唤起。
- 跨仓库搜索、快速记录和每日笔记动作。
- Vault 插件数量、Git、同步与容量状态。
- 自定义封面、主题市场或复杂看板。
- 自动更新、安装包签名和公开分发。
- macOS、Linux 适配。

## 6. 信息架构

MVP 保持单窗口、双视图：

```text
主窗口
├── 仓库首页
│   ├── 顶部栏：产品名 / 主题 / 设置
│   ├── 搜索框
│   ├── 收藏仓库
│   ├── 最近仓库
│   └── 添加仓库
└── 设置
    ├── 外观
    ├── 排序偏好
    ├── Obsidian URI 检测
    └── 关于
```

添加和编辑仓库使用模态对话框，不增加独立页面。

## 7. 核心交互

### 7.1 启动流程

```text
打开 Obsidian Hub
  -> 自动聚焦搜索框
  -> 输入关键词或用方向键选择
  -> Enter 打开目标仓库
  -> 更新最近打开时间
  -> 默认关闭 Hub 窗口
```

若 URI 调用失败，则保留窗口并显示可操作错误，不更新最近打开时间。

### 7.2 键盘规则

- `/` 或 `Ctrl+K`：聚焦搜索框。
- `ArrowUp` / `ArrowDown`：移动当前选择。
- `Enter`：打开当前仓库。
- `Escape`：清空搜索；搜索为空时关闭当前对话框。
- `Ctrl+N`：打开添加仓库对话框。
- `Ctrl+,`：打开设置。

快捷键在实现阶段做冲突检查，MVP 不注册系统级快捷键。

### 7.3 删除语义

UI 使用“从 Hub 移除”，并明确提示：

> 只移除启动器中的记录，不会删除仓库或其中的任何文件。

## 8. 视觉方向

### 8.1 设计原则

- 熟悉：让 Obsidian 用户无需重新学习。
- 轻量：首屏以搜索和仓库选择为中心。
- 克制：减少仪表盘式信息堆积。
- 快速：避免大图、远程资源和阻塞动画。
- 独立：具有自己的产品身份，不伪装成官方 Obsidian 界面。

### 8.2 视觉语言

- 使用深浅中性色作为主背景与层级面。
- 使用紫色作为选择、焦点和主操作强调色。
- 采用紧凑列表或低装饰卡片，而非大封面宫格。
- 圆角、阴影和边框保持克制。
- 字体使用系统 UI 字体，避免额外字体加载。
- 所有状态不能只依赖颜色表达。

### 8.3 初始设计令牌方向

实现前应在项目设计规范中固化以下语义令牌，而不是在组件内写死颜色：

```text
--background-primary
--background-secondary
--background-modifier-hover
--background-modifier-active
--text-normal
--text-muted
--text-error
--interactive-accent
--interactive-accent-hover
--border-subtle
--focus-ring
```

令牌名称可以保留 Obsidian 用户熟悉的语义，但具体值和实现由项目独立维护。

## 9. 技术架构

### 9.1 总览

```text
React presentation
  -> feature/application layer
    -> VaultRepository interface
    -> VaultLauncher interface
    -> SystemPreferences interface
      -> Tauri adapters
        -> Rust commands
          -> filesystem / app data / OS URI handler
```

### 9.2 前端职责

- 渲染仓库列表、搜索、对话框和设置。
- 管理当前选择、焦点和短生命周期 UI 状态。
- 执行搜索、排序等纯逻辑。
- 调用应用服务，不直接访问文件系统或 Tauri API。

### 9.3 Rust/Tauri 职责

- 打开系统目录选择器。
- 规范化并校验 Windows 路径。
- 读取、迁移和原子写入应用配置。
- 生成并打开受限的 `obsidian://` URI。
- 将系统错误转换为稳定的错误码与用户可理解信息。

### 9.4 权限原则

- 不启用通用 shell 命令执行。
- 文件系统权限只覆盖用户主动选择的路径与应用数据目录。
- URI opener 只允许 `obsidian://` 所需范围。
- 不访问仓库中的 Markdown 内容。

## 10. 数据模型

### 10.1 配置草案

```json
{
  "schemaVersion": 1,
  "preferences": {
    "theme": "system",
    "sortMode": "favoriteThenRecent",
    "closeAfterLaunch": true
  },
  "vaults": [
    {
      "id": "018f-example",
      "name": "主知识库",
      "path": "D:\\Obsidian\\Main",
      "description": "个人知识管理",
      "obsidianVaultId": null,
      "favorite": true,
      "createdAt": "2026-07-14T08:00:00.000Z",
      "updatedAt": "2026-07-14T08:00:00.000Z",
      "lastOpenedAt": null
    }
  ]
}
```

### 10.2 字段原则

- `id`：Hub 自己生成的稳定标识，不使用路径或名称充当 React key。
- `path`：保存规范化绝对路径，是判重的主要依据。
- `name`：默认取目录名，允许用户修改，仅用于展示和 URI 降级。
- `obsidianVaultId`：MVP 允许为空；后续可让用户粘贴或从公开操作获取。
- 时间统一保存为 ISO 8601 UTC 字符串。
- 未知字段在读取时按迁移策略处理，不静默破坏配置。

### 10.3 写入策略

1. 序列化到同目录临时文件。
2. 完成写入和关闭。
3. 用替换方式更新正式配置。
4. 写入失败时保留原文件并返回明确错误。

## 11. 仓库添加与校验

### 11.1 添加流程

```text
点击添加
  -> 系统选择目录
  -> 规范化绝对路径
  -> 检查目录可访问
  -> 检查 .obsidian 为目录
  -> 检查是否重复
  -> 预填目录名
  -> 用户确认
  -> 保存配置
```

### 11.2 校验结果

| 状态               | 处理                              |
| ------------------ | --------------------------------- |
| 有效 Obsidian 仓库 | 允许添加                          |
| 目录不存在         | 阻止并提示重新选择                |
| 无 `.obsidian`     | 默认阻止，说明这不是已初始化仓库  |
| 路径已存在         | 聚焦已有条目，不重复添加          |
| 无访问权限         | 阻止并显示权限错误                |
| 名称重复、路径不同 | 允许添加，但提示 URI 名称歧义风险 |

MVP 不提供“创建新 Obsidian 仓库”，只管理已有仓库入口。

## 12. 启动策略

### 12.1 URI 生成

优先级：

1. 有 `obsidianVaultId`：`obsidian://open?vault=<encoded-id>`。
2. 无 ID：`obsidian://open?vault=<encoded-name>`。

所有参数必须使用标准 URI 编码，不允许字符串直接拼接未经编码的用户输入。

### 12.2 名称重名风险

官方 URI 支持名称或 Vault ID，但名称并不天然唯一。因此：

- Hub 以路径判重，不以名称判重。
- 出现同名仓库时，在列表中始终显示路径。
- 同名且均无 Vault ID 时，启动前提示用户补充 ID。
- 在尚未验证按绝对目录路径启动仓库的跨版本行为前，不将其作为唯一主路径。

### 12.3 启动结果

- 系统成功接收 URI 后，记录 `lastOpenedAt`。
- 如果系统无 URI handler、调用被拒绝或参数无效，不更新时间。
- MVP 能确认“URI 已交给系统”，但不能宣称已经获知 Obsidian 完成加载；产品文案必须区分两者。

## 13. 错误模型

稳定错误码草案：

```text
CONFIG_NOT_FOUND
CONFIG_INVALID
CONFIG_UNSUPPORTED_VERSION
CONFIG_READ_FAILED
CONFIG_WRITE_FAILED
VAULT_PATH_NOT_FOUND
VAULT_PATH_FORBIDDEN
VAULT_MARKER_NOT_FOUND
VAULT_DUPLICATE_PATH
VAULT_NAME_AMBIGUOUS
OBSIDIAN_URI_UNAVAILABLE
OBSIDIAN_LAUNCH_FAILED
```

UI 展示用户能采取的下一步，技术细节进入受控日志。不得只显示“发生未知错误”。

## 14. 性能目标

- 100 个仓库条目下，搜索和键盘移动无可感知卡顿。
- 配置读取与首屏渲染不依赖网络。
- 首屏不读取各仓库内容，不递归扫描目录。
- 冷启动性能在真实 Windows 11 安装包中测量，开发服务器数据不作为最终结论。
- 性能测量先建立基线，再决定是否需要状态库、虚拟列表等优化。

## 15. 测试策略

### 15.1 单元测试

- 路径规范化与大小写判重。
- 搜索、收藏和最近使用排序。
- URI 编码与优先级。
- 配置解析、校验与版本迁移。
- 错误码到用户提示的映射。

### 15.2 组件测试

- 空状态和添加仓库流程。
- 搜索结果与键盘导航。
- 收藏、编辑、移除确认。
- 路径失效和名称冲突状态。
- 深浅色与焦点可见性。

### 15.3 Rust 测试

- 有效和无效仓库目录校验。
- 配置原子写入失败保护。
- URI 构造不接受非 Obsidian scheme。
- Windows 路径边界，包括盘符大小写、尾部分隔符和 Unicode。

### 15.4 Windows 手工验收

- 未安装 Obsidian。
- 已安装但目标仓库尚未注册。
- Obsidian 未运行。
- Obsidian 正在运行且打开另一个仓库。
- 仓库名称含空格、中文、`#`、`&` 等字符。
- 两个不同路径的同名仓库。
- 仓库被移动、重命名或磁盘离线。
- 100 个模拟条目下的搜索和键盘体验。

## 16. MVP 验收标准

满足以下全部条件才算 MVP 完成：

1. 用户可以添加一个有效仓库并在重启应用后看到它。
2. 重复路径不会产生两条记录。
3. 搜索、方向键和回车能完成目标仓库启动。
4. 收藏项优先，其余按最近打开排序。
5. 无效路径不会发出启动 URI。
6. 移除条目不会修改或删除仓库文件。
7. 特殊字符名称经过正确 URI 编码。
8. 深色、浅色和系统主题下均可清晰操作。
9. 键盘焦点始终可见，核心控件有可访问名称。
10. 格式、Lint、类型、单元测试和 Debug 构建全部通过。
11. 在 Windows 11 实机完成核心手工验收矩阵。
12. 不存在 TODO、调试输出、无效 import 和被替代的旧实现。

## 17. 里程碑

### 当前迭代：启动器核心版

本迭代合并完成真实仓库配置与高频启动体验：手动添加、AppData 持久化、紧凑仓库列表、搜索、收藏、最近使用排序、路径有效性、键盘导航，以及空、加载、错误和打开中状态。编辑、标签管理、右键菜单、自动扫描、设置页及扩展状态继续留在后续里程碑。

### M0：技术探针

验证 Tauri 2 开发环境、Windows 目录选择、路径校验、`obsidian://` 打开行为以及 Obsidian 已运行时的表现。输出结论，不追求正式 UI。

### M1：可用纵切

完成“添加一个仓库 -> 持久化 -> 展示 -> 打开”的端到端最小闭环。

### M2：完整 MVP

补齐搜索、收藏、最近使用、编辑、移除、异常状态、主题和键盘交互。

### M3：质量与交付验证

完成自动化测试、性能基线、Windows 11 手工验收和本地安装包验证。

### M4：真实使用复盘

至少使用一周，记录启动次数、失败场景和未满足需求，再决定下一阶段。

## 18. 后续路线候选

按真实反馈排序，不提前承诺：

1. 指定根目录扫描仓库。
2. 从 Obsidian 已注册仓库中导入。
3. 系统托盘、单实例与全局快捷键。
4. 快速创建、每日笔记和搜索动作。
5. 跨仓库只读全文搜索。
6. Git、同步和插件状态。
7. 自动更新与签名发布。
8. macOS、Linux 支持。

## 18.1 M5：跨仓库链接 Bridge（已确认）

在不重构现有桌面启动器的前提下，新增 Obsidian Hub Bridge 子项目，完成
`@仓库[[笔记]]` 的搜索、插入、显示和跳转闭环。

- Hub 负责只读扫描已登记仓库、维护版本化 JSON 元数据索引，并通过仅监听
  `127.0.0.1:27124` 的令牌认证 HTTP API 提供搜索、解析、打开和心跳能力。
- Bridge 负责 Obsidian 内的补全、CodeMirror 装饰、阅读模式渲染、点击处理和连接状态；
  不递归扫描外部仓库。
- API 凭据与索引使用独立 AppData 文件，不修改现有 `config.json` schema；索引不保存正文。
- Bridge 安装必须由用户明确触发或预先授权，只写入目标仓库的
  `.obsidian/plugins/obsidian-hub-bridge/`，不修改社区插件启用列表。
- 第一阶段实现普通笔记链接；标题、块和嵌入只在解析器与协议中预留，反向链接面板暂缓。

验收以两个真实仓库之间完成 `@` 仓库补全、笔记补全、阅读显示和点击打开为准；Hub 停止时
Bridge 必须快速失败并提供 Obsidian URI 降级，不阻塞编辑器。

### Bridge 管理闭环（2026-07-15）

仓库列表直接展示 Bridge 的未安装、等待启用、已连接和可更新状态。安装与更新由用户在
对应仓库条目上显式触发，不再依赖添加仓库完成后的浏览器原生确认框；安装后提供明确的
Obsidian 手动启用说明。状态由插件目录、manifest 版本与最近心跳共同决定。

### 跨仓库语法迁移（2026-07-15）

### 20.1 启动页第二轮视觉决策（2026-07-14）

- Hub 的价值是让用户每次自由选择仓库，不强化“继续上次”；最近打开时间只参与排序和辅助信息。
- 所有仓库使用同一种横向列表项，收藏只影响排序与标识，不切换为独立大卡片或双列网格。
- 主页面的友好感由每日入口语、本地时段图标、仓库颜色标记和与当前选择联动的 SVG 星图提供。
- 趣味元素不读取仓库内容、不联网、不引入动画库，并在列表增长时主动退让。

### 20.2 库概览统计决策（2026-07-14）

- 首页增加仓库数、Markdown 笔记数和文件夹数；统计只读，不分析笔记内容。
- 启动时先读取 AppData 中独立的 `overview-cache.json`，随后由 Rust 后台全量刷新，禁止阻塞首屏。
- 文件夹统计排除 `.obsidian`、`.git`、`node_modules`、`.trash`、系统回收站和常见构建缓存目录；仓库根目录本身不计入文件夹数。
- 单个仓库不可访问时跳过并报告实际扫描数量，不让局部错误使整个概览不可用。
- 仓库列表不展示本地路径；路径仍参与搜索、校验、判重和修复。

### 20.3 大屏视觉舞台决策（2026-07-14）

- 默认窗口提高到适合双区布局的尺寸；紧凑窗口仍以仓库列表为唯一视觉核心。
- 宽屏内容最大宽度扩展到约 1520px，左侧操作区与右侧视觉舞台约按 58:42 分配。
- 右侧使用“仓库宇宙 + 中心晶体”作为大型视觉元素，只消费真实仓库、收藏和当前选择数据。
- 超宽屏只扩大视觉舞台与安全留白，不无限拉宽仓库列表；搜索状态继续收拢为单列结果。

## 21. 跨仓库链接 Bridge 规划（待确认）

> 提案日期：2026-07-15
> 状态：等待用户确认后实施

### 21.1 目标

在保留独立 Vault 边界的前提下，为 Obsidian 提供接近原生双链习惯的跨仓库链接：

```md
[[普通笔记]]
@目标仓库[[笔记路径|显示名称]]
```

Hub 负责管理仓库、构建只读笔记目录索引和部署插件；Bridge 插件负责 Obsidian 编辑器内的识别、补全、显示与跳转。仅靠桌面端不能接管 Obsidian 编辑器，因此 Bridge 是必要组成部分。

### 21.2 第一阶段范围

第一阶段只完成一条可验证闭环：

1. 在仓库中输入 `@` 可触发跨仓库仓库选择面板。
2. 选择仓库和笔记后插入 `@仓库名[[相对路径|标题]]`。
3. 编辑模式与阅读模式能将该语法显示为跨仓库链接。
4. 点击链接通过受控的 `obsidian://open?vault=...&file=...` 打开目标笔记。
5. Hub 可将内置 Bridge 构建产物安装到用户明确加入 Hub 的仓库。
6. 新增仓库时，根据用户的一次性偏好自动安装 Bridge；安装失败不影响仓库加入。
7. Hub 展示 `未安装 / 已安装 / 版本过旧 / 状态未知`，不静默修改 Obsidian 的社区插件启用配置。

第一阶段暂不实现：跨仓库反向链接、跨仓库嵌入、标题与块引用、笔记稳定 ID、文件移动自动修复和全局图谱。

### 21.3 目录与职责

```text
packages/obsidian-hub-bridge/
├── manifest.json
├── package.json
├── src/
│   ├── main.ts
│   ├── crossVaultLink.ts
│   ├── suggest.ts
│   └── settings.ts
└── styles.css

src-tauri/src/
├── bridge.rs        # 检测、校验和原子部署 Bridge 构建产物
└── note_index.rs    # 只读扫描已管理仓库的 Markdown 元数据
```

- Bridge 使用独立构建入口，最终只向仓库写入 `manifest.json`、`main.js` 和可选 `styles.css`。
- Hub 只扫描文件名、相对路径和必要的标题/别名元数据；不记录正文，不把完整用户路径写入日志。
- 插件部署仅作用于用户已明确添加到 Hub 的仓库，并提供全局开关和单仓库覆盖选项。
- 自动安装指复制插件文件，不代表自动启用；Hub 不关闭受限模式，也不篡改用户的启用插件列表。

### 21.4 数据与安全

- 跨仓库目标首版以 `仓库显示名 + 相对 Markdown 路径` 表达，源码保持可读。
- Hub 内部继续以规范化绝对路径识别仓库；重名仓库若缺少稳定 Vault ID，则禁止生成有歧义的跨仓库链接并提示修复。
- Bridge 包随 Hub 本地构建产物分发，部署前校验版本和必需文件；首版不从网络下载或执行远程代码。
- 覆盖旧版本前先写临时目录并替换必需文件，不删除用户仓库或其他插件内容。
- 插件版本升级需要明确提示；不在 Obsidian 运行期间静默破坏正在加载的插件。

### 21.5 验收标准

1. Bridge 可在一个真实测试仓库中加载，普通 `[[...]]` 行为不受影响。
2. `@` 搜索能先选择仓库，再按标题与相对路径检索笔记，并排除当前仓库。
3. 插入结果可解析、可渲染、可点击，中文、空格、`#`、`&` 等字符经过正确编码。
4. 目标仓库或笔记不存在时显示可操作错误，不静默失败。
5. Hub 能检测并安装 Bridge 到已授权仓库；新增仓库遵循自动安装偏好。
6. Hub 不自动启用社区插件，不修改除 Bridge 自身目录之外的仓库配置或内容。
7. 插件单元测试、Hub 前后端测试、类型检查、Lint 与 Debug 构建通过。
