### 2.1.0-preview.1：事件日志与写入恢复

#### 范围与交互

1. 记录以下用户显式操作：
   - `noteCreated`：从 Echo 创建 Main、从 Main 创建 Output。
   - `taskUpdated`：任务完成或恢复。
   - `echoReviewUpdated`：Echo 标为已阅或恢复待处理。
2. 工作台底部增加低干扰的“活动”入口，弹窗按时间倒序显示最近事件，可刷新并清空全部活动；不在主页增加新卡片或分栏。
3. 新笔记创建成功后，在本次应用会话中保留“最近创建结果”。如果 Obsidian 打开失败，错误提示旁提供“重新打开”，不得再次调用创建接口；重新扫描或关闭应用不删除已创建文件。
4. 错误提示继续使用现有 `AppError.code`，前端针对目标冲突、文件变化、仓库离线、权限/写入失败和 Obsidian 打开失败提供可执行提示，不用字符串猜测错误类型。

#### 事件模型

新增稳定 DTO：

```text
WorkflowEventV1
├── schemaVersion: 1
├── id: UUID
├── occurredAt: ISO 8601 UTC
├── kind: noteCreated | taskUpdated | echoReviewUpdated
├── outcome: succeeded | failed
├── source?: { vaultId, relativePath }
├── target?: { vaultId, relativePath }
├── detail?: { noteKind | complete | reviewed }
└── errorCode?: string
```

- 不保存标题、任务正文、笔记正文、绝对路径、错误原文、密钥或 token；界面展示名称时通过当前登记表和相对路径组合。
- 日志文件为预览版 AppData 下的 `workflow-events-v1.jsonl`，UTF-8、每行一个完整 JSON。单行大小设硬上限，总文件默认保留最近 2,000 条且不超过 2 MiB。
- 写入采用进程内互斥、追加、flush 与 `sync_data`。轮转使用同目录临时文件、保留最新完整行并原子替换；不得在仓库目录写日志。
- 读取逐行校验：尾部最后一行截断时忽略并报告 `hasWarnings`；中间损坏行跳过并计数，不让整个活动列表不可用。超大行、未知 schema 和无效枚举均作为损坏行处理。
- 清空由用户在活动弹窗二次确认后显式触发，使用原子替换为空文件；只清事件日志，不改变笔记、任务、已阅状态或仓库配置。

#### 操作与日志的一致性

- 业务文件和工作流状态仍是真实事实源，事件日志只是可重建的活动记录，不承担跨文件事务。
- 先完成并校验业务写入，再追加 `succeeded` 事件。事件写入失败不得把已经成功的笔记创建报告成失败，否则用户重试可能产生重复文件。
- 命令返回值增加可选 `eventWarning`；业务成功但事件未记录时，前端显示非阻断提示。任务和已阅操作同样保留成功状态。
- 业务动作失败时尽力追加 `failed` 事件，只记录错误码。失败事件记录本身失败时仍返回原始业务错误，不覆盖根因。
- `open_workspace_note` 不写事件；它不是知识流状态变化。创建成功后的自动打开失败也不得修改已记录的 `noteCreated` 成功事件。

#### 模块与接口

- 新增 Rust `workflow_events` 模块，独立承担 DTO、路径、追加、读取、轮转和清空；`workspace_actions` 与 `workspace_state` 不直接操作日志文件。
- 在 Tauri 命令编排层调用业务动作与事件记录，新增 `load_workflow_events`、`clear_workflow_events`，并让三个写命令返回带 `eventWarning` 的稳定结果。
- 前端在 `src/domain/workspace.ts` 定义镜像 DTO，通过 `VaultGateway` 访问；新增活动弹窗组件，WorkspacePage 只负责打开、重试和局部状态更新。
- 不修改 `config.json` 和 `workspace-state.json` schema，不引入数据库或新运行时依赖。UUID 使用 Rust 现有随机能力生成 RFC 4122 v4 字符串，避免仅为 ID 引入依赖。

#### 测试与验收

- Rust：追加/读取顺序、并发追加、2,000 条与 2 MiB 轮转、尾部截断、中间坏行、未知 schema、清空、AppData 边界、业务成功但日志失败、业务失败事件。
- 前端：活动排序与空/警告/错误状态；清空二次确认；三个动作的成功事件；`eventWarning` 非阻断；创建成功后打开失败只重试打开、不重复创建。
- 回归：来源文件不被修改；任务乐观更新不整页刷新；Bridge 仍只读；preview.3 用户配置与工作流状态无迁移。
- 完成格式、Lint、类型、前端、Bridge、Rust、安全边界和签名本地构建。先本地验收；提交、推送和发布 `2.1.0-preview.1` 必须再次取得用户明确授权。

### 2.1.1-preview.1：文件监听与局部索引

在 2.1.0 实机稳定后另行细化。预定边界：Rust 监听登记仓库、事件去抖与路径归一化、单文件重新解析、Tauri 事件推送、前端局部合并、预览变更提示、离线降级。实施前需评估 `notify` 依赖、Windows 重命名事件语义、网络盘行为和退出清理，不在 2.1.0 预埋后台线程。

### 2.1.2-preview.1：安全撤销与诊断

在事件模型和监听稳定后另行细化。首批撤销只考虑任务完成/恢复和 Echo 已阅/恢复，并在执行前重新校验当前状态与内容摘要。不会自动删除已创建的 Main/Output；涉及删除必须单独确认。诊断导出只包含版本、错误码、仓库 ID、相对路径和脱敏事件，不包含正文或绝对路径。

## 2.0 之后的产品路线图（2026-10-04，规划完成、分阶段待确认）

### 总体判断

2.0 已完成 Echo → Main → Output 的跨仓库人工知识流、仓库角色配置、任务处理、只读预览和独立更新通道。后续不再以增加首页组件为目标，而是依次解决四个问题：流程是否可靠、关系是否可追踪、内容是否可检索、AI 是否能在不夺走正文控制权的前提下提供帮助。

持续遵守以下产品边界：

- Hub 仍是单页工作入口与跨库协调层，不复制 Obsidian 编辑器，不在 Hub 编辑正文。
- Bridge 保持只读；所有写入仍由 Hub 在用户显式操作后执行，并继续校验角色、路径、并发与冲突。
- 默认不持久化正文，不把用户知识上传到外部服务；任何正文索引或 AI 传输都必须单独说明、显式启用并可清理。
- 每个阶段独立规划、实施、验证和发布。未确认下一阶段前，不顺手实现后续能力。

### 2.1：可靠性与可恢复性

目标：让 Hub 从“流程可用”进入“长期使用不怕出错”。

1. **本地事件日志**
   - 为创建 Main、创建 Output、任务完成/恢复、Echo 已阅/恢复等显式操作记录结构化事件。
   - 使用追加写、可截断修复的版本化 JSONL；只保存事件类型、时间、仓库 ID、相对路径、结果和错误码，不保存正文、密钥或无必要绝对路径。
   - 事件日志用于最近活动、故障诊断与有限恢复，不作为笔记内容的第二事实来源。
2. **增量文件感知**
   - Rust 侧监听已登记仓库 Markdown 变化，按仓库与相对路径合并短时间内的重复事件，仅重扫受影响文件。
   - 创建、修改、删除、改名和仓库离线分别形成稳定 DTO；前端局部更新列表、任务和当前预览，不整页闪烁。
   - 监听失败必须降级为手动刷新，不能阻止工作台使用；Bridge 是否共享监听能力另行评估，不以 HTTP 为新依赖。
3. **写入恢复与错误分类**
   - 创建成功但 Obsidian 打开失败时保留结果并提供重新打开，不允许重复创建。
   - 明确区分内容变化、目标冲突、仓库离线、权限不足、路径失效与协议打开失败。
   - 任务失败继续回滚；新建文件继续采用不覆盖与落盘校验。仅对具有明确逆操作且未发生后续修改的事件提供撤销。

数据决策：实施前先定义 `WorkflowEventV1`、日志轮转上限和损坏恢复规则。事件 ID 使用 UUID；笔记引用仍以 `vaultId + relativePath` 为主，内容摘要用于并发校验。该阶段不修改用户 Markdown frontmatter，不引入数据库。

验收：应用异常退出后日志可继续读取；单文件变化不触发全库扫描；高频保存不会产生事件风暴；离线仓库不影响其他仓库；失败动作不丢文件、不重复创建；事件日志可由用户清空。

### 2.2：工作流状态与关系

目标：让 Hub 能回答“这条灵感走到了哪里、下一步应该处理什么”。

1. **轻量流程状态**
   - Echo：待处理、已阅、已转化、暂缓。
   - Main：思考中、可输出、已输出。
   - Output：草稿、完成；“已发布”只有在未来存在明确发布动作后再加入。
   - 状态默认保存在 Hub 工作流状态中，不自动改写用户正文；删除状态只影响 Hub 视图。
2. **来源与下游关系**
   - 解析 Hub 创建笔记中的受控来源字段与跨库链接，形成 Echo → Main → Output 关系。
   - 展示来源、引用资料、下游笔记和断链，不制作自由拖拽知识图谱。
   - 新建笔记可增加稳定 `hub_id`；既有笔记继续使用仓库 ID + 路径兼容，不批量改写。改名追踪优先使用稳定 ID，无法确定时只提示用户确认。
3. **统一待处理队列**
   - 在现有单页工作台内增加状态筛选与排序，不恢复多栏 Dashboard。
   - 队列可包含待处理 Echo、思考中的 Main、可输出认知、空正文新笔记和长期未继续内容。
   - 默认排序应可解释，允许按最近修改、阶段和仓库筛选；不使用不透明的“智能优先级”。

数据决策：实施前设计版本化 `WorkflowStateV2` 和迁移测试，旧 reviewed/todayPlan 无损读取；状态与关系可完全由本地状态、受控 frontmatter 和仓库文件重建。涉及 schema 迁移时必须再次取得确认。

验收：完整流程关系可追溯；状态重启后保持；旧配置无损迁移；文件改名、删除、离线和重复稳定 ID 都有明确降级；首页仍保持单页、紧凑和小窗口可用。

### 2.3：检索与阅读增强

目标：在不建立第二份正文仓库的前提下，提升跨库查找和阅读能力。

1. **分层搜索**
   - 第一层扩展标题、路径、别名、标签和受控 frontmatter 字段，保持轻量即时。
   - 第二层提供用户显式触发的跨库正文搜索；先评估按需流式扫描与本地倒排索引的性能和隐私，再选择实现。
   - 若持久化索引，必须只保存必要 token/位置、设置体积上限、支持一键清理，并明确其可能泄露正文关键词；默认策略需在实施计划中单独确认。
2. **预览能力**
   - 增加 Obsidian 原生 `[[内部链接]]`、Callout、脚注、标题目录与搜索命中高亮。
   - 数学公式需先评估依赖体积；本地图片与附件仅在复用 Rust 真实路径边界校验后加载，不允许 WebView 直接读取任意文件。
   - 保持原始 HTML 不执行、正文不缓存、快速切换不显示旧请求结果。
3. **断链检查**
   - 定期或手动检查 Hub 创建的跨库链接，分类为在线、目标改名、目标删除、仓库离线和名称歧义。
   - 自动修复只适用于稳定 ID 唯一匹配；其他情况必须用户确认，不批量猜测目标。

验收：常见规模仓库的搜索延迟与内存有基线；清理索引后可完全重建；附件越界、恶意协议和原始 HTML 均被拒绝；断链修复不误改用户笔记。

### 3.0：可检查的 AI 辅助

目标：AI 帮助找材料、提问题和组织思路，但正文控制权仍属于用户。

1. 用户从 Main、Knowledge 和可选 Echo 中显式选择来源，Hub 生成可预览的上下文包；默认不自动发送整库内容。
2. 第一阶段只支持问题清单、相关资料建议、反例检查和提纲，不直接覆盖 Main 或正式 Output。
3. AI 结果先进入独立草稿或导出结果，保留来源引用、模型信息和生成时间；用户确认后再创建 Output。
4. Provider、密钥存储、网络传输、费用与隐私必须另立安全方案。没有明确协议前，优先提供可复制/导出的上下文包，不内置供应商 SDK。
5. 检索结果和模型回答均视为不可信输入，不得绕过路径校验、执行 HTML、调用通用 shell 或自动写入用户笔记。

验收：发送前可看见准确的来源与预计内容范围；取消操作不产生文件；生成失败不影响来源；结果引用可回到本地原笔记；关闭 AI 后 2.x 全部能力仍可独立工作。

### 交付顺序与决策门

```text
2.1 事件与增量更新
  → 2.2 状态与关系
    → 2.3 搜索与阅读
      → 3.0 AI 上下文
```

- 先实施 2.1 的事件模型与增量索引原型，再决定是否进入完整文件监听；事件日志是 2.2 关系与活动的基础。
- 2.2 开始前必须确认工作流状态字段、是否给新笔记写入 `hub_id`、以及旧 reviewed 状态的迁移方式。
- 2.3 正文搜索开始前必须用真实仓库规模比较流式扫描与持久索引，确认隐私、磁盘占用和清理策略。
- 3.0 开始前必须确认 AI Provider、授权方式、上下文上限、费用提示和草稿落点；不得把它并入普通 2.x 修复版本。
- 每阶段均运行格式、Lint、类型、前端、Bridge、Rust、安全边界、性能基线和 Windows 实机验证。发布仍使用独立预览通道，是否进入正式版另行决定。

暂不规划：多人协作、云同步、移动端、自由画布知识图谱、自动发布平台、自动移动或删除来源、后台静默更新、无人确认的 AI 写作。

## 任务静默更新与 Markdown 预览优化（2026-10-04 已确认实施）

- 任务勾选改为行内乐观更新：仅锁定当前任务并立即更新勾选状态，不触发全工作台 `refresh()`、不清空列表、不改变当前分页和滚动位置。后端成功后用返回的新内容摘要同步同一来源文件的任务与笔记；失败时回滚原快照并在原页面提示错误。完整扫描只保留给手动刷新、创建笔记等确有必要的动作。
- 把预览解析从弹窗组件中拆为独立、安全的 React Markdown 渲染模块，不引入可执行 HTML 或 Obsidian 运行时。补齐 YAML frontmatter、ATX 标题、段落与硬换行、嵌套有序/无序/任务列表、连续引用、围栏代码、分隔线、GFM 表格，以及粗体、斜体、删除线、行内代码、普通 Markdown 链接和现有跨库链接；原始 HTML 继续按纯文本展示，外部链接使用系统浏览器前需保持安全协议白名单。
- 扩大预览弹窗的可用宽高并让正文成为唯一弹性滚动区；页头、文件信息和底部操作固定可见。长路径可换行，表格和代码块局部横向滚动，正文、列表、引用、标题间距统一，小窗口不得裁掉正文或操作按钮。
- 增加任务成功/失败无全量刷新、同文件摘要同步、复杂 Markdown 结构、安全 HTML、长正文滚动与响应式布局测试；完成格式、Lint、类型、前端测试和本地构建。不提交、推送或发布，除非用户后续明确要求。

## 1. 一句话定义

Obsidian Hub 是一个在 Obsidian 加载任何仓库之前运行的轻量桌面启动器，让多仓库用户先选择目标仓库，再直接进入对应工作空间。

## 2. 问题与机会

### 2.1 用户问题

Obsidian 默认延续最近使用的仓库。多仓库用户想进入另一个仓库时，往往需要：

1. 先启动上一次使用的仓库。
2. 等待该仓库的主题、索引与社区插件初始化。
3. 再打开仓库切换器。
4. 选择真正需要的仓库。

当上一次使用的是插件很多的主仓库时，这段无效等待尤其明显。

### 2.2 根因

普通 Obsidian 插件只能在某个仓库已经被选定并开始加载后运行，因此无法真正拦截“启动前选择仓库”。独立启动器可以把选择动作提前到 Obsidian 进程启动之前。

### 2.3 核心假设

如果启动器能够快速、可靠地展示仓库并支持键盘直达，用户会愿意把它固定到任务栏，替代 Obsidian 原始图标成为日常入口。

### 2.4 成功信号

- 用户能够在启动器出现后 3 秒内选中并打开目标仓库。
- 从启动器操作到系统接收 Obsidian URI 的中位耗时低于 300 ms，不含 Obsidian 自身加载时间。
- 日常使用中无需先加载错误仓库。
- 核心流程完全支持键盘，不强迫用户使用鼠标。
- 连续使用一周后，用户愿意保留任务栏入口。

## 3. 已确认的产品决策

| 决策     | MVP 选择                | 原因                               |
| -------- | ----------------------- | ---------------------------------- |
| 平台     | Windows 11 优先         | 对准当前真实环境，缩短验证周期     |
| 仓库录入 | 仅手动添加              | 避免扫描复杂度，先验证核心启动价值 |
| 视觉     | Obsidian 原生感         | 降低学习成本，形成连续的使用体验   |
| 产品形态 | 独立 Tauri 应用         | 在 Obsidian 仓库加载前运行         |
| 配置存储 | AppData 中的版本化 JSON | 数据规模小、透明、易备份与迁移     |
| 仓库访问 | 默认只读                | 启动器不应侵入用户知识库           |

“Obsidian 原生感”只指视觉语义和交互习惯，不代表依赖 Obsidian 内部样式，也不等于官方兼容认证。

## 4. 用户与场景

### 4.1 核心用户

- 长期、熟练使用 Obsidian。
- 同一设备管理多个用途不同的仓库。
- 主仓库启用大量插件，冷启动较慢。
- 经常在主仓库、项目仓库、临时仓库之间切换。

### 4.2 核心场景

#### 场景 A：打开轻量仓库

用户上次使用主仓库，现在只想快速进入临时仓库。启动 Hub、搜索仓库、回车，主仓库完全不参与此次启动。

#### 场景 B：在相似仓库中定位

用户有多个项目仓库。启动 Hub 后直接输入项目名，列表实时过滤，选择目标并打开。

#### 场景 C：常用仓库直达

用户收藏 3 个高频仓库。Hub 默认先展示收藏项，方向键选择并回车打开。

#### 场景 D：仓库路径已经移动

Hub 检测到原路径无效，不发送错误启动请求，而是提示编辑路径或移除条目。

## 7. 核心交互

### 7.1 启动流程

```text
打开 Obsidian Hub
  -> 自动聚焦搜索框
  -> 输入关键词或用方向键选择
```

- `Escape`：清空搜索；搜索为空时关闭当前对话框。
- `Ctrl+N`：打开添加仓库对话框。
- `Ctrl+,`：打开设置。

## 8. 视觉方向

### 8.1 设计原则

- 熟悉：让 Obsidian 用户无需重新学习。
- 轻量：首屏以搜索和仓库选择为中心。
- 克制：减少仪表盘式信息堆积。
- 快速：避免大图、远程资源和阻塞动画。
- 独立：具有自己的产品身份，不伪装成官方 Obsidian 界面。

### 8.2 视觉语言

- 使用深浅中性色作为主背景与层级面。
- 使用紫色作为选择、焦点和主操作强调色。
- 采用紧凑列表或低装饰卡片，而非大封面宫格。
- 圆角、阴影和边框保持克制。
- 字体使用系统 UI 字体，避免额外字体加载。

## 9. 技术架构

### 9.1 总览

```text
React presentation
  -> feature/application layer
    -> VaultRepository interface
    -> VaultLauncher interface
    -> SystemPreferences interface
      -> Tauri adapters
        -> Rust commands
          -> filesystem / app data / OS URI handler
```

### 9.2 前端职责

- 渲染仓库列表、搜索、对话框和设置。
- 管理当前选择、焦点和短生命周期 UI 状态。
- 执行搜索、排序等纯逻辑。
- 调用应用服务，不直接访问文件系统或 Tauri API。

### 9.3 Rust/Tauri 职责

- 打开系统目录选择器。
- 规范化并校验 Windows 路径。
- 读取、迁移和原子写入应用配置。
- 生成并打开受限的 `obsidian://` URI。
- 将系统错误转换为稳定的错误码与用户可理解信息。

### 9.4 权限原则

- 不启用通用 shell 命令执行。
- 文件系统权限只覆盖用户主动选择的路径与应用数据目录。
- URI opener 只允许 `obsidian://` 所需范围。
- 不访问仓库中的 Markdown 内容。

## 10. 数据模型

### 10.1 配置草案

```json
{
  "schemaVersion": 1,
  "preferences": {
    "theme": "system",
    "sortMode": "favoriteThenRecent",
    "closeAfterLaunch": true
  },
  "vaults": [
    {
      "id": "018f-example",
      "name": "主知识库",
      "path": "D:\\Obsidian\\Main",
      "description": "个人知识管理",
      "obsidianVaultId": null,
      "favorite": true,
      "createdAt": "2026-07-14T08:00:00.000Z",
      "updatedAt": "2026-07-14T08:00:00.000Z",
      "lastOpenedAt": null
    }
  ]
}
```

### 10.2 字段原则

- `id`：Hub 自己生成的稳定标识，不使用路径或名称充当 React key。
- `path`：保存规范化绝对路径，是判重的主要依据。
- `name`：默认取目录名，允许用户修改，仅用于展示和 URI 降级。
- `obsidianVaultId`：MVP 允许为空；后续可让用户粘贴或从公开操作获取。
- 时间统一保存为 ISO 8601 UTC 字符串。
- 未知字段在读取时按迁移策略处理，不静默破坏配置。

### 10.3 写入策略

1. 序列化到同目录临时文件。
2. 完成写入和关闭。
3. 用替换方式更新正式配置。
4. 写入失败时保留原文件并返回明确错误。

| 无 `.obsidian`     | 默认阻止，说明这不是已初始化仓库  |
| 路径已存在         | 聚焦已有条目，不重复添加          |
| 无访问权限         | 阻止并显示权限错误                |
| 名称重复、路径不同 | 允许添加，但提示 URI 名称歧义风险 |

MVP 不提供“创建新 Obsidian 仓库”，只管理已有仓库入口。

## 12. 启动策略

### 12.1 URI 生成

优先级：

1. 有 `obsidianVaultId`：`obsidian://open?vault=<encoded-id>`。
2. 无 ID：`obsidian://open?vault=<encoded-name>`。

所有参数必须使用标准 URI 编码，不允许字符串直接拼接未经编码的用户输入。

### 12.2 名称重名风险

官方 URI 支持名称或 Vault ID，但名称并不天然唯一。因此：

- Hub 以路径判重，不以名称判重。
- 出现同名仓库时，在列表中始终显示路径。
- 同名且均无 Vault ID 时，启动前提示用户补充 ID。
- 在尚未验证按绝对目录路径启动仓库的跨版本行为前，不将其作为唯一主路径。

### 12.3 启动结果

- 系统成功接收 URI 后，记录 `lastOpenedAt`。
- 如果系统无 URI handler、调用被拒绝或参数无效，不更新时间。
- MVP 能确认“URI 已交给系统”，但不能宣称已经获知 Obsidian 完成加载；产品文案必须区分两者。

### 20.1 启动页第二轮视觉决策（2026-07-14）

- Hub 的价值是让用户每次自由选择仓库，不强化“继续上次”；最近打开时间只参与排序和辅助信息。

- 主页面的友好感由每日入口语、本地时段图标、仓库颜色标记和与当前选择联动的 SVG 星图提供。
- 趣味元素不读取仓库内容、不联网、不引入动画库，并在列表增长时主动退让。

### 20.2 库概览统计决策（2026-07-14）

- 首页增加仓库数、Markdown 笔记数和文件夹数；统计只读，不分析笔记内容。
- 启动时先读取 AppData 中独立的 `overview-cache.json`，随后由 Rust 后台全量刷新，禁止阻塞首屏。
- 文件夹统计排除 `.obsidian`、`.git`、`node_modules`、`.trash`、系统回收站和常见构建缓存目录；仓库根目录本身不计入文件夹数。
- 单个仓库不可访问时跳过并报告实际扫描数量，不让局部错误使整个概览不可用。
- 仓库列表不展示本地路径；路径仍参与搜索、校验、判重和修复。

## 21. 跨仓库链接 Bridge 历史规划（已实施，后续以当前决策为准）

> 提案日期：2026-07-15
> 状态：核心功能已实施，部分历史设计已由当前决策替代

### 21.1 目标

在保留独立 Vault 边界的前提下，为 Obsidian 提供接近原生双链习惯的跨仓库链接：

```md
[[普通笔记]]
@目标仓库[[笔记路径|显示名称]]
```

Hub 负责管理仓库、构建只读笔记目录索引和部署插件；Bridge 插件负责 Obsidian 编辑器内的识别、补全、显示与跳转。仅靠桌面端不能接管 Obsidian 编辑器，因此 Bridge 是必要组成部分。

### 21.2 第一阶段范围

第一阶段只完成一条可验证闭环：

1. 在仓库中输入 `@` 可触发跨仓库仓库选择面板。
2. 选择仓库和笔记后插入 `@仓库名[[相对路径|标题]]`。
3. 编辑模式与阅读模式能将该语法显示为跨仓库链接。
4. 点击链接通过受控的 `obsidian://open?vault=...&file=...` 打开目标笔记。
5. Hub 可将内置 Bridge 构建产物安装到用户明确加入 Hub 的仓库。
6. 新增仓库时，根据用户的一次性偏好自动安装 Bridge；安装失败不影响仓库加入。
7. Hub 展示 `未安装 / 已安装 / 版本过旧 / 状态未知`，不静默修改 Obsidian 的社区插件启用配置。

第一阶段暂不实现：跨仓库反向链接、跨仓库嵌入、标题与块引用、笔记稳定 ID、文件移动自动修复和全局图谱。

### 21.3 目录与职责

```text
packages/obsidian-hub-bridge/
├── manifest.json
├── package.json
├── src/
│   ├── main.ts
│   ├── crossVaultLink.ts
│   ├── suggest.ts
│   └── settings.ts
└── styles.css

src-tauri/src/
├── bridge.rs        # 检测、校验和原子部署 Bridge 构建产物
└── note_index.rs    # 只读扫描已管理仓库的 Markdown 元数据
```

- Bridge 使用独立构建入口，最终只向仓库写入 `manifest.json`、`main.js` 和可选 `styles.css`。
- Hub 只扫描文件名、相对路径和必要的标题/别名元数据；不记录正文，不把完整用户路径写入日志。
- 插件部署仅作用于用户已明确添加到 Hub 的仓库，并提供全局开关和单仓库覆盖选项。
- 自动安装指复制插件文件，不代表自动启用；Hub 不关闭受限模式，也不篡改用户的启用插件列表。

### 21.4 数据与安全

- 跨仓库目标首版以 `仓库显示名 + 相对 Markdown 路径` 表达，源码保持可读。
- Hub 内部继续以规范化绝对路径识别仓库；重名仓库若缺少稳定 Vault ID，则禁止生成有歧义的跨仓库链接并提示修复。
- Bridge 包随 Hub 本地构建产物分发，部署前校验版本和必需文件；首版不从网络下载或执行远程代码。
- 覆盖旧版本前先写临时目录并替换必需文件，不删除用户仓库或其他插件内容。
- 插件版本升级需要明确提示；不在 Obsidian 运行期间静默破坏正在加载的插件。

### 21.5 验收标准

1. Bridge 可在一个真实测试仓库中加载，普通 `[[...]]` 行为不受影响。
2. `@` 搜索能先选择仓库，再按标题与相对路径检索笔记，并排除当前仓库。
3. 插入结果可解析、可渲染、可点击，中文、空格、`#`、`&` 等字符经过正确编码。
4. 目标仓库或笔记不存在时显示可操作错误，不静默失败。
5. Hub 能检测并安装 Bridge 到已授权仓库；新增仓库遵循自动安装偏好。
6. Hub 不自动启用社区插件，不修改除 Bridge 自身目录之外的仓库配置或内容。
7. 插件单元测试、Hub 前后端测试、类型检查、Lint 与 Debug 构建通过。

### 21.6 跨仓库只读预览

- 点击跨仓库链接默认在当前 Obsidian 窗口打开原生风格只读浮窗，不自动切换仓库。
- Hub 通过受认证接口按索引记录定位 Markdown，并在校验仓库根目录、相对路径、扩展名与文件大小后读取正文。
- Bridge 内存中只保存当前浮窗的一篇正文；关闭或打开下一篇时释放上一份内容，不创建中转笔记。
- 浮窗使用 Obsidian Markdown 渲染器，首版保证正文 Markdown；跨仓库附件与嵌入资源暂不承诺完整解析。
- 浮窗提供“在目标仓库打开”，仅在用户明确操作时调用 Obsidian URI。
- 跨仓库链接沿用 `internal-link` 视觉，不显示箭头、外链背景图或额外伪元素。

### 21.7 分层文件浏览

- 选择仓库后只返回根目录的直接子文件夹与 Markdown 文件，不一次铺平全部笔记。
- 选择文件夹进入下一级，并通过当前路径继续递归浏览；候选列表提供返回上一级。
- 在当前目录输入文字时，服务端递归检索该目录树内的文件名、标题、别名和相对路径。
- 浏览与搜索响应返回总数和是否还有结果；Bridge 通过“加载更多”逐批扩大结果窗口。
- 文件夹优先于文件，名称按不区分大小写排序；最终仍序列化为稳定的 `@仓库[[路径]]`。

## 24. Obsidian Hub 2.0 第一阶段（2026-10-02，实施中）

实施分支：`codex/obsidian-hub-2.0`，从当前 `master` 创建。2.0 的规划后续修改、代码、测试和构建均在该分支进行；`master` 保持 1.0 版本基线。未经用户确认，不合并、不提交、不推送、不发布。

### 24.1 产品判断

2.0 不重写现有 Hub + Bridge，而是在已验收的启动、登记、跨库浏览和只读预览之上增加“角色、聚合、工作流”三层能力。第一阶段目标是让 Echo → Main → Output 的人工知识流真正跑通；AI 只预留上下文边界，不在本阶段开发 Agent、Embedding、GraphRAG、向量数据库或自动改写。

Knowledge Vault 是 Main 的旁路增强来源，不是强制流转节点。Hub Vault 只承载 MOC、Workspace、Workflow、模板和中间稿，不保存业务知识的最终版本，也不得逐步演化成第五个 Main Vault。

### 24.2 第一阶段范围

包含：

1. 为登记仓库配置 `hub`、`echo`、`main`、`knowledge`、`output`、`other` 角色，并要求五个核心角色在参与工作流前唯一且路径有效。
2. 初始化或校验 Hub Vault 的 `00 Home/`、`01 MOC/`、`02 Topics/`、`03 Workspace/Cognition/`、`03 Workspace/Output/`、`03 Workspace/Scratch/`、`04 Workflow/`、`05 System/Templates/`、`05 System/Registry/`、`05 System/Config/` 目录约定。初始化必须由用户显式触发。
3. 建立 Hub 桌面端聚合索引，提供 Today、全局任务、Echo Inbox、Processing Inbox、Continue Working、Recent Activity、Recent Knowledge、Recent Cognition、Recent Output、Knowledge Flow 和 Vault Status 所需数据。
4. 提供标题、路径、别名与标签级的跨 Vault 搜索；首阶段不做正文全文检索。
5. 实现四个显式工作流动作：`Develop`、`Promote to Main`、`Create Output`、`Publish to Output`。
6. 全局任务继续以原 Markdown 为事实来源；Today Plan 只保存用户当日选择的任务引用，不复制任务正文成为第二份事实来源。
7. 保留现有 Vault 启动、Bridge 安装、跨库链接、预览和手动更新能力。

暂缓：

- Claudian 内部 API 集成、自动检索和自动改写；第一阶段只定义可供后续使用的显式上下文 DTO。
- 正文全文搜索、向量索引、Knowledge Graph、自动知识搬运、自动生成认知。
- Git、同步、容量分析、后台守护、静默更新、公开发布和跨平台正式支持。
- Echo 的自动 Archive 语义；在归档目录和 frontmatter 规则确认前，只提供 Reviewed 状态。

### 24.3 数据与架构决策

2.0 预览版使用独立应用标识 `io.github.obsidian-hub.v2preview`、独立安装名称和 AppData。首次运行只读导入 1.0 正式版 `config.json`，复制到预览版专属目录后迁移为 schemaVersion 2；不改写正式版配置。预览版内部的 `config.json` 是其唯一登记事实来源，Bridge 安装时读取该预览登记表。正式版与预览版并行使用时，后续仓库登记变更不会自动双向同步。预览包不生成正式更新签名产物，不要求或使用正式版私钥。

预览版配置结构：

```text
AppConfigV2
├── preferences（沿用现有字段）
├── vaults[]
│   ├── 现有 VaultEntry 字段
│   └── role: hub | echo | main | knowledge | output | other | null
└── workspace
    ├── hubVaultId
    └── initializedAt
```

- schemaVersion 1 自动迁移到 2；旧仓库 `role` 默认为 `null`，不得依据名称猜测角色。
- Bridge 继续只读登记表，并同时接受 schemaVersion 1 与 2 中它需要的 `id/name/path` 字段。
- 新聚合模块放在 Rust 侧，负责受限扫描、实时文件校验、任务解析和稳定 DTO；React 不直接访问 Tauri 或文件系统。
- 聚合缓存与配置分离。磁盘缓存只保存可重建的文件元数据和扫描时间，不保存笔记正文或任务正文；任务文本仅保留在进程内存。
- 复用唯一的忽略目录、Markdown 元数据与路径校验规则，逐步消除 `overview`、`note_index` 和 Bridge 本地索引之间的重复实现。
- 新增写入能力不经过 Bridge。Bridge 保持跨库读取、预览、链接与打开职责；Hub 的 Rust 应用服务承载所有用户显式触发的文件创建、任务勾选和跨 Vault 移动。

建议模块边界：

```text
React pages/features
  -> dashboard/workflow/task/search services
    -> typed Tauri gateway
      -> workspace_index（只读聚合）
      -> workspace_actions（显式写入）
        -> validated vault roots + atomic file operations
```

### 24.4 写入与并发安全

2.0 会改变当前“默认只读”的产品边界，实施前必须同步更新 `CLAUDE.md` 与 `AGENTS.md`。允许的写操作只包括：

- 在用户指定的 Hub Vault Workspace 中创建中间稿。
- 用户点击 Promote/Publish 后，将对应 Workspace 文件移动到已配置的 Main/Output Vault。
- 用户点击任务复选框后，修改来源 Markdown 中匹配的单个 task marker。
- 保存 Today Plan、Reviewed 状态等 Hub 自身工作流状态。

每次写入必须同时满足：仓库角色已配置、真实路径位于登记根目录内、拒绝符号链接逃逸、Markdown 扩展名白名单、目标冲突不覆盖、临时文件加原子替换、写前校验文件修改时间或内容摘要。源文件已变化时返回冲突，让用户刷新后重试，不做静默合并。

Promote/Publish 默认采用“目标落盘成功并校验后移除 Workspace 源文件”的移动语义；这是文件删除效果，必须由本计划确认一并取得授权。失败时保留源文件，禁止产生半完成状态。

### 24.5 工作流元数据

Workspace 草稿使用受控 frontmatter，保留来源与血缘，不直接改写原始 Echo/Main 正文：

```yaml
hub_id: <uuid>
hub_stage: cognition-draft | output-draft
origin:
  vault_id: <id>
  path: <relative-path>
derived_from:
  - vault_id: <id>
    path: <relative-path>
references: []
created_at: <ISO-8601>
```

- `Develop`：复制 Echo 正文到 Cognition Draft，并记录来源；不自动删除或改写 Echo。
- `Promote to Main`：移动 Cognition Draft 到 Main，保留 lineage frontmatter。
- `Create Output`：以 Main 为来源创建 Output Draft，不修改 Main。
- `Publish to Output`：移动 Output Draft 到 Output，保留 lineage frontmatter。
- 同名目标必须要求用户更名或取消，不自动覆盖，也不静默追加序号。
